# Controlled dual hosting

GitHub remains the source of truth. The repository default branch is `main`. The existing public-pricing workflow runs on push and pull request using Node 24, the root lockfile, Playwright Chromium, unit/release checks, the normal build and browser checks. `vercel.json` defines the SPA rewrite. It contains no deployment trigger or approval policy. No Vercel workflow, configuration, integration, production branch or approval setting is changed by this LOT. Verify the actual Vercel branch, triggers, deployment protection and approval settings in the dashboard before making any assumptions about them.

## Workflow triggers

| Event and ref | Validation | Artifact retention | Deployment |
| --- | --- | --- | --- |
| Pull request opened, updated or reopened against `feat/dl-video-ux-04` or `main` | Checks the PR merge SHA in the canonical repository | Separate TEST and FAILOVER archives and checksums are verified on the runner | Skipped |
| Push to a feature branch without a PR | Existing pricing workflow | None from this workflow | Skipped |
| Manual dispatch on `main` with matching full SHA and default `deploy_test=false` | Checks that immutable SHA | Separate TEST and FAILOVER downloads, seven days | Skipped |
| Manual dispatch on `main` with matching full SHA and `deploy_test=true` | Same checks | Same downloads | Requires a protected ref, environment approval and explicit activation |
| Manual dispatch on any other branch, or SHA mismatch | Skipped for other refs, fails for a mismatched SHA on main | None | Skipped |

A stacked Draft PR targeting `feat/dl-video-ux-04` can validate before this workflow lands on `main`. GitHub can require first-time fork approval and can skip `pull_request` runs for merge conflicts. GitHub requires the workflow file on the default branch for `workflow_dispatch`. Follow checks in the PR before that point. [GitHub workflow events](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows)

Both paths run the root lockfile install, three builds, unit, release, privacy date, pricing browser, consent, Audit funnel, portal, Cloudflare and video checks. The date checker cannot establish the actual privacy publication date. The pricing workflow remains the ordinary feedback path and overlaps some gates. This workflow has no provider secrets or environment in the verification job. Its GitHub token has read-only repository permissions and checkout discards its credentials. Keep Cloudflare credentials and the activation variable exclusive to the protected environment. Repository-level secrets can be available to same-repository PR workflows, so do not put deployment credentials there. PRs and dispatches have separate concurrency groups. GitHub can supersede queued runs in the same group.

The deploy job verifies the same-run TEST checksum, mode, source SHA and run attempt. Immediately before upload it checks the Pages project name, subdomain and a configured production branch distinct from `ci-test`. Cloudflare routes non-production branch deployments to preview URLs. With that mapping, the fixed Wrangler upload to `ci-test` updates `https://ci-test.digital-lab-backup.pages.dev` while the root deployment stays active. Wrangler 4.166.0 is locked separately and runs outside the repository with only the static upload files. Actions are pinned to full SHAs. Live project settings and behavior still require authorized verification. Keep the production branch setting stable during publication because the preflight and upload are separate calls. [Cloudflare preview deployments](https://developers.cloudflare.com/pages/configuration/preview-deployments/) · [Get Pages project API](https://developers.cloudflare.com/api/resources/pages/subresources/projects/methods/get/)

Before releasing the job, reviewers should check the exact SHA and test evidence. TEST keeps live requests inert, GA4 disabled and Pages pages out of indexes. FAILOVER is a separate, SHA-labelled, checksummed artifact with an explicit DO-NOT-DEPLOY label. It is never downloaded by the deploy job. No custom domain is attached. See the [artifact behavior and local fallback](DL-CLOUDFLARE-BACKUP-02.md).

## Activation after separate approval

1. Save the workflow on the feature branch and open a Draft PR against `feat/dl-video-ux-04`. Confirm the PR checks pass and the deployment job is skipped. Later, after separate authorization, review and land the approved parent stack and this workflow on protected `main` through the existing release process. Confirm the Vercel policy first because changing main can trigger the existing integration. Do not dispatch from feature branches.
2. On GitHub, create the `cloudflare-test` environment. Restrict it to the exact protected branch `main`, configure required independent reviewers, prevent self-review, and disable administrator bypass where available. The public repository supports these protections. GitHub requires one approval from its configured reviewers. If the owner is the sole eligible reviewer and starts the run, preventing self-review leaves nobody able to approve. Add an independent eligible reviewer or keep deployment disabled. Leave the environment activation variable unset while establishing these controls. Restrict writes and review workflow changes on main.
3. Separately confirm that `digital-lab-backup` is the existing Direct Upload project for the intended account, its production branch is configured and differs from `ci-test`, and the preview alias is available for this purpose. Keep the standalone standby site and DNS as-is.
4. After authorization, the owner can provision an expiring token using **Account → Cloudflare Pages → Edit** for **only the account containing this project**, then enter it as the **environment secret** `CLOUDFLARE_API_TOKEN`. Add `CLOUDFLARE_ACCOUNT_ID` as an environment variable. Only after verifying the branch restriction and independent approval, set the environment variable `CLOUDFLARE_TEST_DEPLOY_ENABLED=true`. Grant no DNS, Workers, or other account access. Pages Edit is account-level, so the token may modify other Pages projects in that account. The account/project/branch checks narrow workflow behavior, while token compromise still has account-wide Pages impact. Do not place the token in repo files, logs, comments or chat. [Cloudflare CI token guidance](https://developers.cloudflare.com/pages/how-to/use-direct-upload-with-continuous-integration/)
5. Run the workflow on `main` with the exact full SHA and `deploy_test=false`. Confirm the browser gates, TEST and FAILOVER artifact identities, SHA-256 files and absence of a deployment job. Confirm current account usage and review the npm audit findings before any publishing approval.
6. In a separately authorized run, set `deploy_test=true`, supply the exact SHA, and approve only the `cloudflare-test` deployment. The job checks the uploaded marker against the same SHA and run, then checks CSS/JS, noindex, the TEST CSP, deep links, retired portal notices, and closed legacy email API paths. It fails on stale assets or unsafe HTTP behavior. Do not treat a completed upload as a passed smoke check. If Preview is access-controlled, plan an independently authorized validation path before enabling the job. The implemented smoke checks use no credentials.

## Readiness

Local review is ready for a stacked Draft PR. Live deployment remains gated on a passing GitHub PR run, confirmation of the existing Vercel release behavior, protected main and environment settings, an independent reviewer, an audit disposition, and verified Cloudflare production-branch/preview routing. If the Pages API supplies no production branch, let preflight fail and review the existing Direct Upload configuration with the owner. For the first authorized preview, capture the root deployment identity from Cloudflare before dispatch and confirm it stays the same afterward. The mocked HTTP smoke checks cannot establish live edge behavior.

## Operations and capacity

- **Failure and rollback:** Keep the last known-good TEST archive and its SHA-256 privately. A failing preflight makes no upload. If an upload succeeds and the checks fail, stop, inspect the run and Cloudflare deployment logs, and use the known-good TEST artifact for an owner-approved restore to the same preview branch. Do not promote a failed deployment or use a production rollback for this preview. Never restore FAILOVER to the preview alias.
- **Manual fallback:** Verify the TEST archive against its SHA-256, extract it, verify the TEST marker and upload only its contents using the existing project’s Preview flow. Use `ci-test` only after confirming it is the preview branch. Repeat the post-upload checks. Do not upload `dist` or FAILOVER.
- **Credential rotation:** Replace the environment secret with a new short-lived account-scoped Pages Edit token during approved maintenance. Verify the next authorized test and revoke the previous token. Revoke immediately on suspected exposure and inspect Pages deployment activity. Do not print or export either token.
- **Cost:** Target €0 incremental recurring. Cloudflare Free static asset serving is free. Direct Upload uses a prebuilt artifact and does not schedule a Pages Git build. Cloudflare documents 500 hosted builds/month, a 20-minute limit and one concurrent build on Free. Wrangler uploads on Free are limited to 20,000 files and 25 MiB per asset. Both local artifacts have 145 files and their largest file is 8,411,382 bytes. Cloudflare retains the latest 100 deployments and the active production deployment, with a 30-day retention window for older previews. Standard hosted runners are free for this public repository. PR validation consumes runner capacity and retains no downloadable artifacts. Each dispatch retains two compressed archives for seven days (approximately 100 MB combined per run). Use the validation-only default and count only authorized uploads against any applicable Cloudflare deployment and API limits. Verify current artifact usage and applicable account limits before activating uploads. [Pages limits](https://developers.cloudflare.com/pages/platform/limits/) · [Pages pricing](https://developers.cloudflare.com/pages/functions/pricing/) · [GitHub Actions billing](https://docs.github.com/en/billing/concepts/product-billing/github-actions)
- **Later synchronization:** After the owner approves explicit release criteria and proves a preview run, consider triggering the exact approved main release SHA from a protected release gate. Keep the default preview-only destination, independent approval and immutable artifact handoff, and rate-limit or coalesce releases. Leave Vercel's production workflow and approval rules separate. Automatic synchronization is not enabled.
